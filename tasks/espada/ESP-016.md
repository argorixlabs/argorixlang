# ESP-016 — The first native backend

Status: DONE (pending review and CI on `main`)
Lane: Claude.
Dependencies: ESP-015 (PR #60, merged as `main@31b82d1`).
Date: 2026-09-24.

## Observable objective

Take the C compiler off the path of compiling Argorix. The work:

- specify registers, stack, calling conventions, layout and alignment,
  relocations and the object format;
- implement instruction selection, an initial register assignment and
  object emission;
- link with a declared linker;
- port or bound the host shim.

No complex optimization until the backend conforms. The deliverables are a
native backend in `.argx`, object and ABI fixtures, and binaries.

## Acceptance criteria (Plan Espada)

- [x] **It compiles Core and the whole compiler without writing C or
      running a C compiler.**
      - `compiler/native.argx` writes an ELF64 object. The system linker
        links it with the runtime shim.
      - The native compiler builds itself to a fixed point in a container
        with no C compiler, no Rust and no network.
      - It compiles and runs every fixture there.
- [x] **Calls, integers, branches, arenas and errors behave as in the
      transitional backend.**
      - Same results on the fixture suites.
      - Same results on a differential over the whole package corpus.
      - Same results on 480 generated programs checked against the spec
        oracle, 335 of which trap.
      - Same refusals, with the same reasons.
- [x] **The system libraries and the linker are inventoried, and what
      rebuilding the shim needs is declared separately.**
      - `bootstrap/native/toolchain.json` names the linker, the C library,
        the shim (its sources, symbols and retirement plan), the link line,
        and the C compiler that only rebuilding the shim needs.
      - Each run records the versions and digests of the host's copies in
        `native-report.json`, and the shim's in `shim.json`.

## Design

`spec/core/native-x86-64.md` is the specification. In short:

- **One program, two backends.**
  - The native backend starts from the C backend's tables and whole-program
    checks (`compiler.c_emit.prepare`).
  - It walks each body as that backend does, and writes machine code where
    the C backend writes a C statement.
  - So both refuse the same programs for the same reasons, and run the same
    program with the same order of effects.
  - What C leaves unevaluated (literals, locals, and places behind bounds or
    handle checks) is kept as a node and evaluated where the C would
    evaluate it.
- **Frames.**
  - Every value lives in memory, in frame slots reused as C blocks close.
  - Registers are assigned by a fixed rule: operands go to RAX, RCX, RDI and
    RSI for the instruction or call at hand. There is no allocator.
  - A call passes its arguments in a block at the bottom of the caller's
    frame, the budget in RDI and the result's address in RDX.
  - The program runs on a stack sized for the deepest call its depth budget
    allows, so running out of depth is a typed trap.
- **Layout.** As a C compiler lays out the C backend's definitions on
  x86-64, since the runtime's limits count bytes.
- **The shim.** The C1 runtime and small wrappers, compiled once by a C
  compiler.
  - The symbols native code calls, their ABI, memory ownership and traps are
    listed in the specification and in `toolchain.json`.
  - It holds no phase of the toolchain.
  - Its retirement (inline checks, and buffers and arenas in Argorix over a
    narrower C library interface) is planned after this task.
- **Placement.** The plan names `compiler/codegen/native/`. The modules sit
  next to the C backend instead (`compiler/x86.argx`, `compiler/elf.argx`,
  `compiler/native.argx`), as `compiler/c_emit.argx` does.

## Evidence

Local, on Ubuntu 24.04 (GNU ld 2.42, glibc 2.39):

- **Encoder** (`native.rs`, `the_encoder_matches_gnu_as_when_available`):
  8,823 instructions, every form over every register and base, identical to
  what GNU `as` assembles.
- **Linking** (`a_native_object_links_and_runs_when_binutils_are_available`):
  an object written by `compiler/elf.argx` links with `ld` and runs.
- **Against the C backend**
  (`the_native_backend_matches_the_c_backend_when_binutils_are_available`),
  over the 191 packages of the differential corpus, stage1 compiling each
  with both backends:
  - 86 programs run with the same exit status, standard output and
    standard error;
  - 42 are refused for the same reason;
  - 63 fail to check with the same diagnostics;
  - one root is not UTF-8 and is skipped, as in the other differentials.
- **Against the spec oracle** (`bootstrap/native.py cases`): 480 programs
  from `core-c-harness generate`, seeds 1 to 6, all with the expected result
  or trap. Between them they call every runtime symbol the backend can call.
- **The fixture suites:** all 87 cases (runtime, stdlib, lexer, parser,
  checker, IR, C backend, pipeline, stage1 and the regression corpus) pass
  natively. Objects written by stage1 and by the native compiler are the
  same.
- **The native bootstrap** (`bootstrap/native.py`), in an empty network
  namespace, with only `python3`, `ld` and `ldd` on the path, and
  `--require-no-c-compiler --require-no-network --require-rust-free-host`:
  - native1, native2 and native3 write the seed's object and manifest, byte
    for byte, and are byte-identical executables;
  - native3 writes `stage1.c` when asked for C;
  - relocating the sources and reordering the modules change nothing;
  - the 87 cases pass, and native2 and native3 write the same object for
    each;
  - a reworded diagnostic reaches the new compiler's output in one
    generation;
  - with the backend's immediates edited, `.text` grows from 1,443,732 to
    1,628,676 bytes in generation 2, and generation 3 is a fixed point. The
    edited backend changes another program's code but not what it does.
- **Speed:** the compiler builds itself in 1.9 s natively, against 1.2 s
  for the C build at `-O2`.
- **CI** (`core-c.yml`):
  - `Native seed and runtime shim (ESP-016)`: the last step with a C
    compiler;
  - `Native bootstrap without a C compiler, Rust or network (ESP-016)`:
    `bootstrap/container/native/Dockerfile`, which is `debian:stable-slim`
    with binutils, the C library and Python, run with `--network none`;
  - `Native backend against the spec oracle (ESP-016)`.

## Scope and limits

- **One target.** Linux x86-64 only; Windows and the second bootstrap are
  ESP-017.
- **Trusted base.** The linker, the C library and the shim objects are
  trusted: recorded, not verified. The seed comes from stage1, and so from
  stage0's C; equal generations do not rule out a defect that reproduces
  itself (ESP-023, MAT-023).
- **No optimization, no debug information.** Every value is in memory and
  every checked operation is a call. The executable has one symbol,
  `main`.
- **The stack reservation** is sized by the largest frame times the depth
  limit: 2 GiB of address space for the compiler at the default depth. It
  is mapped without reserving swap and committed as it is used. On a host
  with strict overcommit the mapping can fail, and the program traps with
  `OUT_OF_MEMORY` before it runs.
