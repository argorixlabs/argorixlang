# ESP-017 — The second target and the native bootstrap

Status: DONE (pending review and CI on `main`)
Lane: Claude.
Dependencies: ESP-016 (PR #61, merged as `main@5e881ac`).
Date: 2026-09-26.

## Observable objective

Native self-compilation on both supported systems, Linux and Windows:

- add the Windows x86-64 object format and ABI, and paths, Unicode and I/O;
- run the stage2/stage3 bootstrap with the native backend on each system;
- check library references and the architecture;
- document minimal debugging and symbols.

The deliverables are two bootstrap matrices, native binaries and a build
guide.

## Acceptance criteria (Plan Espada)

- [x] **Both environments rebuild and run without Rust or a C compiler for
      Argorix sources.**
      - Linux: ESP-016's native bootstrap. The compiler builds itself to a
        fixed point in a container with no C compiler, no Rust and no
        network.
      - Windows (this task): `bootstrap/native-windows.ps1 bootstrap`, with
        only `link.exe` and the system directory on the path.
        `-RequireNoCCompiler` and `-RequireRustFreeHost` find neither.
        - native1, native2 and native3 write the seed's object, manifest and
          diagnostics, byte for byte, and are byte-identical executables.
        - The 87 fixture cases pass natively.
- [x] **Hashes are compared within one fixed environment, never across
      systems.**
      - Each bootstrap compares its own generations and cases.
      - A Windows object and a Linux object for the same package differ by
        design (COFF and ELF, different ABIs); nothing compares them.
- [x] **A system that is not validated stays unsupported.**
      - The targets are exactly `x86_64-linux` and `x86_64-windows`.
      - The build file refuses any other name: "the target is `x86_64-linux`
        or `x86_64-windows`".

## Design

`spec/core/native-x86-64.md`, section "Windows x86-64", is the
specification. In short:

- **One program, two targets.**
  - The code generator writes the same program for both. Only three things
    differ: the object format, how the runtime is called, and how the
    program gets its stack.
  - The target travels as the last of the limits, so no signature changed.
    The manifest names it.
- **COFF** (`compiler/coff.argx`) takes the same input as the ELF writer:
  - one `.text` section, the read-only data after the code;
  - a `REL32` relocation per runtime call;
  - the relocation-count overflow record past 65,534 relocations.
- **Calls to the runtime.** Arguments are loaded as for System V. Each call
  then moves them to the Microsoft registers and reserves the 32-byte area
  the callee may use, with the fifth argument above it. Program functions
  keep their own convention.
- **Stack.** Windows grows a thread's stack through a guard page, and its C
  library checks frames against the thread's own stack. So:
  - `main` runs the program on a thread whose stack reserves the size Linux
    maps;
  - every frame is probed a page at a time.
- **Host.** The C1 host boundary had a stub on Windows that refused every
  operation. It now does what the POSIX one does, over the wide API:
  - the command line in UTF-16;
  - paths from UTF-8;
  - roots and files resolved through open handles to their final paths,
    in `\\?\` form;
  - reads through the checked handle;
  - writes that refuse a reparse point.
- **Bootstrap without Python.** `bootstrap/native-windows.ps1` runs the
  seed, the linker copy, the generations, the suites and any `cases.json`.
  It is PowerShell, which Windows ships.
- **Executables.** Each native compiler is an x86-64 console program that
  imports only `KERNEL32.dll` and `SHELL32.dll`, because the C library is
  linked in statically. The bootstrap reads that from the PE headers and
  fails otherwise. Stage0's own `argorixc.exe`, which imports
  `VCRUNTIME140.dll` and the CRT DLLs, is refused by the same check.

## Evidence

Local, on Windows 11 x86-64 (10.0.26340), MSVC 14.29 (Visual Studio 2019
Build Tools) and Windows SDK 10.0.19041:

- **Stage1 on Windows.**
  - MSVC `cl` builds stage1 from stage0's C, with warnings as errors.
  - Stage1 compiles itself in 1.6 s and writes stage0's C byte for byte.
  - Before ESP-017.A it returned 8000007 (the host refused every file).
- **The first native program.** `tests/selfhost/runtime/buffer_success.argx`,
  compiled to COFF, linked by `link.exe`, prints `ARGORIX_RESULT:42`.
- **The native bootstrap,** with only the copied linker on the path, and
  `-RequireNoCCompiler -RequireRustFreeHost`:
  - native1, native2 and native3 write the seed's 1,857,330-byte object
    byte for byte;
  - they are one 1,909,760-byte executable;
  - the native compiler builds itself in 2.9 s. Built by `cl /O2`, stage1
    takes 1.6 s;
  - 87 of 87 fixture cases pass, with the same object from native2 and
    native3. The cases include the stdlib host cases, which read and write
    files through the Windows boundary;
  - the standalone linker writes the same executable as the one in the
    developer environment.
- **Negative controls.**
  - With the frame probe removed, the native compiler built from the
    mutated seed dies on its own sources with an access violation
    (0xC0000005). Its 44 KiB frames skip the guard page.
  - Stage0's `argorixc.exe` fails the executable check.
- **Against the spec oracle** (`native-windows.ps1 cases`): the 480 programs
  of `core-c-harness generate`, seeds 1 to 6 (the ones ESP-016 runs on
  Linux), all give the result or trap the oracle expects. They were compiled
  one by one with only the linker on the path, in 112 s.
- **Linux unchanged.** Every `argorixc` test passes in Docker, including the
  differential of the native backend against the C backend over the package
  corpus. The one test that pins the build file's key list was updated for
  `target`.
- **CI** (`core-c.yml`, `native-windows`, on `windows-latest`):
  - the seed with `cl`;
  - the linker copied out;
  - the bootstrap with only that linker on the path;
  - the oracle's 480 programs.

## Scope and limits

- **Two targets.** Linux x86-64 and Windows x86-64. Any other system or
  architecture stays unsupported.
- **Network.** The Windows bootstrap does not isolate the network as the
  Linux container does (`--network none`). It opens no connection; nothing
  enforces that yet.
- **Trusted base.** `link.exe`, the static C library, `kernel32` and
  `shell32`, and the shim objects are trusted: recorded, not verified. The
  seed comes from stage1, and so from stage0's C, as on Linux (ESP-023,
  MAT-023).
- **The shim** still needs a C compiler to rebuild. Its retirement is
  follow-up work: checks inline, and buffers and arenas in Argorix.
- **Debugging.** There is no PDB and no debug information. The
  specification lists the minimal tools per system.
