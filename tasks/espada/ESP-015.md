# ESP-015 — Stage2/stage3 bootstrap without Rust

Status: DONE (pending review and CI on `main`)
Lane: Claude.
Dependencies: ESP-014 (PR #59, merged; CI green on `main@9054379`).
Date: 2026-09-24.

## Observable objective

Show the self-compilation cycle with no hidden help. Stage1 compiles the
same sources to stage2, and stage2 to stage3, with fixed tools and flags.
The suite runs with stage2 and stage3. Timestamps, paths and order are
controlled. Access to stage0, Rust, caches and the network is removed. Real
changes to a diagnostic and to a function of the compiler show that no
prebuilt seed is being copied.

## Acceptance criteria (Plan Espada)

- [x] Stage2 and stage3 are binary-identical in the agreed deterministic
      environment. Stage1, stage2 and stage3 write byte-identical C,
      manifests and diagnostics, and their executables are byte-identical.
      Nothing is normalized; the build is made deterministic instead:
      - each stage's C is compiled under the same name, from a directory at
        the same depth;
      - with the same flags and environment.
- [x] Conformance with stage2 and stage3: every case of the C fixture
      suites (87) is compiled by both. They write the same C, and it passes
      the case.
- [x] Differences in metadata are resolved, not normalized. The only one
      found, the source file's name in the executable's symbol table, is
      removed by compiling every stage under the same name.
- [x] The limit is explicit: equal stages do not prove the absence of a
      malicious compiler. The report and this card say so.

## What `bootstrap/selfhost.py` does

It starts from `stage1.c`, which stage0 wrote (`bootstrap/stage1.py emit`,
ESP-014). Everything after that needs a C compiler and Python only.

1. **Generations.** Each stage's C is compiled as `compiler.c` in its own
   directory, `stage1/`, `stage2/` and `stage3/`, all at the same depth.
   The same flags and runtime path are used every time, in a fixed
   environment (`LC_ALL=C`, `TZ=UTC`, no ccache). Each stage compiles the
   sources `argorix.build` lists, and its C is the next stage's.
   - Required: the three stages write the same C, manifest and diagnostics;
     their C is stage0's; and the three executables are byte-identical.
2. **Paths and order.** Stage3 builds the same sources twice more:
   - copied under another directory, which must give identical outputs;
   - with the `module` lines reversed, which must give identical C and a
     manifest that differs only in the order of its sources.
3. **The suite.** It covers the cases of `tests/selfhost/{runtime, stdlib,
   lexer, parser, check, ir, c, pipeline, stage1}/cases.json` and the backend
   regression corpus. Each case is compiled by stage2 and by stage3 with the
   locked set the fixture harness gives stage0: the root's directory,
   `compiler/` and `stdlib/`. The two must write the same C. It is then
   built with the C profile and run with the case's host roots and budgets,
   and its exit status, output and build files are checked against the case.
4. **No prebuilt seed.** Two edits to a copy of the compiler's sources:
   - *A diagnostic* (`compiler/check.argx`): `unknown name` becomes
     `no local or constant is named`. Stage3 compiles the edited sources to
     different C. That compiler reproduces itself in one generation, and it
     reports the new wording where stage3 reports the old one.
   - *A function of the backend* (`compiler/c_emit.argx`): the header the C
     backend writes. Generation 1, compiled by stage3, still writes the old
     header. Generation 2 writes the new one, and nothing else changes. It
     is a fixed point: generation 3 writes the same C. The edited backend
     also changes the C of another program.
5. `selfhost-report.json` records:
   - the source revision and the stage0 record;
   - the host, its Rust tools (none) and its network interfaces (only
     loopback);
   - the C compiler, its version, flags and runtime;
   - every stage's digests, and the results of every step.

`--require-rust-free-host` fails if `rustc`, `cargo` or `rustup` exists.
`--require-no-network` fails if the process sees a network interface besides
loopback; the check reads `/proc/net/dev`, which follows the network
namespace.

## Evidence

- **Locally, gcc 13.3:** run in an empty network namespace
  (`unshare -rn`, `--require-no-network`), everything passes in about two
  and a half minutes:
  - the three C files are one file (sha256 `64dbd804…`) and equal stage0's;
  - the three executables are one file (sha256 `3bdab3bd…`);
  - relocating and reordering change nothing they should not;
  - the 87 cases pass with stage3, and stage2 writes the same C for each;
  - both edits propagate as described.
- **Locally, clang 18:** the same results.
- **CI** (`core-c.yml`, `Stage2 and stage3 without Rust or network`, with
  gcc and with clang): the environment is `bootstrap/container/Dockerfile`,
  `debian:stable-slim` with a C compiler, its C library and Python. The
  bootstrap runs with `docker run --network none`, with both requirements
  on. The report and the base image's digest are uploaded.

## Scope and limits

- **Trusting trust.** Equal stages show that the compiler reproduces itself
  from its sources. They do not show that stage0, which wrote `stage1.c`,
  carries no defect that also reproduces itself (a trusting-trust attack).
  Diverse double compilation is ESP-023 and MAT-023.
- **Trusted tools.** The C compiler and its C library are trusted: recorded,
  not verified. The C backend stays in the path until ESP-016.
- **Base image.** CI records the base image's digest with each report but
  does not pin it; a request for the digest from here was rate-limited.
  Pinning it is a change to the Dockerfile's `FROM` line.
- **Identity across toolchains.** Executables are identical within one
  toolchain. gcc and clang build different executables from the same C, as
  expected. Comparing across platforms or compilers is out of scope, as the
  plan says for ESP-017.
