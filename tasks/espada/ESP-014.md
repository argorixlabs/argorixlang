# ESP-014 — The first complete self-hosted compiler

Status: DONE (pending review and CI on `main`)
Lane: Claude.
Dependencies: ESP-013 (PR #58, merged; CI green on `main@89d67d0`).
Date: 2026-09-24.

## Observable objective

Put the Core pieces together into a usable compiler: `compiler/main.argx`,
the bootstrap configuration, and a first interface. Stage0 builds stage1;
stage1 compiles all of its own sources; no Rust process or helper remains
on its path. The deliverables are stage1 and a manifest of its origin,
sources, tools and hashes.

## Acceptance criteria (Plan Espada)

- [x] Stage1 can build a working compiler from its complete sources, not
      just a "hello world" or a parser. It writes, byte for byte, the C
      stage0 wrote for it. That C, compiled, is a compiler that does the same
      build again and writes the same files (C.).
- [x] Every phase of the compiler is Argorix: lexer, parser, linker,
      checker, diagnostics, IR, C emission, manifest and driver. C is still
      the declared transitional backend, and the provenance says so.
- [x] Stage1 and a manifest of its origin, sources, tools and hashes:
      `bootstrap/stage1.py` writes `stage1-provenance.json`, which CI
      uploads.

## ESP-014.A — diagnostics

- The checker (`compiler/check.argx`) and the linker (`compiler/link.argx`)
  now record, for each diagnostic, the span it points at and its message.
  Each message is worded as stage0 words it:
  - every semantic and resolution message;
  - types displayed as stage0 displays them, with the linked name
    (`a__b__Name`) of a type from another module;
  - names that stage0 sorts, in its order: missing fields, missing variants,
    and bindings moved inside a loop.
- A syntax error keeps the span of the token it points at.
- `compiler/report.argx` renders a package's diagnostics as
  `argorixc core-emit-c` prints them (`CoreDiagnostic::render`):
  - `file:line:column: phase[Code]: message`;
  - then the source line, with carets under the span;
  - blank lines between diagnostics.
- Only one file is reported, as stage0 does:
  - the root, when it does not lex or parse;
  - otherwise the first module, in link order, that does not link or check.
- The checker's `Diagnostic` type is now `Finding`, so a module can import it
  alongside the lexer's `Diagnostic`.

**Evidence.**

- `stage1_diagnostics_match_stage0_when_cc_is_available`
  (`crates/argorixc/tests/link_differential.rs`) runs
  `tests/selfhost/stage1/render_files.argx` over the 189 packages of the
  differential. It compares each rendering with stage0's for the same files,
  byte for byte, and all agree:
  - 64 packages do not check;
  - 39 are refused by the C backend (ESP-014.D);
  - 86 are emitted, and both write nothing.
- One root is not UTF-8 and is not compared: stage0 refuses to read it before
  it lexes anything.
- `tests/selfhost/check/samples/messages.src` covers the messages the corpus
  left out, and names sorted in stage0's order.

## ESP-014.B — the driver

`compiler/main.argx` is stage1's entry point. The compiler-host profile gives
a program no command line, environment or directory listing
(`spec/core/stdlib.md`). So a build is described by `argorix.build` at the
root of the package the driver lends: its root file, the files of its locked
set, and the files to write. The format and the results are in
`spec/core/stage1.md`.

- `argorix.build` at the repository root builds the compiler itself. It
  lists `compiler/main.argx` and every module of `compiler/` and `stdlib/`:
  the set stage0 uses for that root with `--stdlib stdlib`. A test keeps
  the list in step with the directories.
- The driver reads the sources and compiles them with `compiler.pipeline`.
  It writes the C, the manifest and the diagnostics.
- It reports each other outcome in its result and in words:
  - a package that does not check, or that the backend refuses;
  - a build file that is not valid;
  - a file the host cannot read.

**Evidence** (`crates/argorixc/tests/stage1.rs`):

- `stage1_builds_itself_when_cc_is_available`: stage0 builds stage1, and
  stage1 compiles its own 24 sources. See C. below.
- `stage1_reports_each_outcome_when_cc_is_available`. Each outcome is checked
  against stage0's command line where it has one:
  - a two-module program: stage0's C, which runs;
  - a failure in a dependency and in the root: stage0's text, and no C;
  - a refused program: stage0's text;
  - six build files that are not valid;
  - a missing file, and a path that leaves the package.

## ESP-014.C — stage1, bootstrapped

`bootstrap/stage1.py` has two steps, which may run on different hosts.

- `emit` is stage B0 (`bootstrap/architecture.md`). Stage0 writes the C of
  `compiler/main.argx` and its locked set to `stage1.c`, and records its own
  identity and the Rust toolchain it was built with.
- `build` is stage B1, and needs only a C compiler. It compiles `stage1` with
  the C1 runtime, then runs it on its own sources and checks that:
  - its C is stage0's, byte for byte;
  - its manifest names every source with the right size and SHA-256, and the
    output;
  - the C it wrote, compiled, is a compiler that does the same build again
    and writes the same three files;
  - no executable loads a Rust library, and, with
    `--require-rust-free-host`, no `rustc`, `cargo` or `rustup` exists on the
    host.
- It writes `stage1-provenance.json` (the deliverable), with:
  - the source revision;
  - stage0, its version and toolchain, and its command;
  - the C compiler, its version, flags and the runtime's digests;
  - the build file and every source's digest;
  - the digest of every artifact, and each executable's shared libraries;
  - `bootstrap_dependency: rust`, as `spec/provenance.md` (P1-02) requires
    until ESP-017.

**Evidence.**

- Locally, with gcc 13 and clang 18, stage1 builds itself in about a second.
  Its C is identical to stage0's and to the rebuilt compiler's.
- It loads only `libc`.
- CI (`core-c.yml`):
  - `Emit stage1 with stage0 (ESP-014)` runs `emit` once.
  - `Stage1 builds itself without Rust` runs `build` with gcc and with clang
    in a `debian:stable-slim` container with no Rust toolchain, and uploads
    the provenance.
  - `tests/selfhost/stage1/cases.json` runs stage1 (an emitted package and a
    failing one) and the renderer under gcc, clang and the sanitizers. Every
    expected file was checked against stage0's command line.

## ESP-014.D — the C backend's refusals

- Every refusal of `compiler/c_emit.argx` now carries the reason stage0's
  backend gives for the same refusal. `c_emit.refusal` returns it as
  `argorixc core-emit-c` prints it: `CBackendUnsupported: <reason>`. Stage1
  writes it to its diagnostics file.
- Where the port tested two of stage0's conditions at once, the test is split
  in two, so each gets its own message.
- Names follow stage0's order:
  - the first function, in name order, that returns a slice;
  - otherwise the first struct, then the first enum, that holds one.
- An intrinsic that is not defined names its receiver as Rust's `{:?}`
  prints stage0's type.

**Evidence.**

- The rendering differential (A.) now also passes a package that checks
  through stage0's backend, and compares the refusal. All 39 refusals agree.
- `tests/selfhost/stage1/refusals/` holds one program for each refusal a
  checked program can reach (nine, eight distinct messages). Each was checked
  against stage0's command line.
- The backend's other refusals are defensive: the checker's rules keep
  programs away from them. They are worded from stage0's source, but no
  program in the corpus reaches them.

## Scope and what remains

- Stage1 is built by stage0, and C is its only backend. Stage2 and stage3
  without stage0 or Rust, with the same flags and binary identity, are
  ESP-015. So is a change to a diagnostic and to a function of the compiler,
  to show that no prebuilt seed is being copied.
- The script compiles stage1 and the rebuilt compiler from files with
  different names, and the executables differ only by that name in their
  symbol tables. Compiled from the same path, they are byte-identical
  (checked locally with gcc 13). Fixing the names and flags so that stage2
  and stage3 are binary-identical is ESP-015's work.
- The build file stands in for a command line because the compiler-host
  profile has none. Package and lock files (`argorix.toml`, MAT-003) are not
  read yet.
