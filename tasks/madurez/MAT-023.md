## Objetivo

Preservar independencia y confianza en cada release, no solo una vez.

## Responsabilidad y alcance

Build, firma, distribución y procedencia.
Las rutas de entregables son propuestas relativas a la raíz: comprobar su existencia antes de usarlas. Implementación de producto en Argorix cuando el bootstrap requerido esté disponible; no introducir Rust como dependencia nueva para cerrar la tarea. Preservar baseline, paper y cambios ajenos.

## Entradas y preparación

- Leer el plan maestro, esta ficha, instrucciones locales aplicables y contratos de las dependencias.
- Verificar el commit actual y estado de Git; registrar abajo cualquier diferencia frente a la base de planificación.
- Exigir evidencia de cierre de cada dependencia. Un texto que afirma estar hecho no sustituye logs, pruebas y artefactos.
- Identificar requisitos MAT-001 y garantías MAT-002 que la tarea satisface. Para tareas iniciales, producir o refinar esos vínculos.
- Fijar comandos, entorno y resultados esperados de la prueba antes de implementar.

## Pasos de implementación

1. Generar SBOM y manifiestos de fuentes, semilla, dependencias y herramientas.
2. Firmar distribución con gestión operativa separada de claves de test.
3. Verificar artefactos en runners limpios y por plataforma.
4. Controlar scripts/hooks y retirar dependencias comprometidas con procedimiento de emergencia.
5. Ejecutar las pruebas indicadas; guardar resultados y discrepancias. Corregir y repetir las pruebas afectadas.
6. Actualizar contratos, documentación y esta ficha con evidencias y dependencias restantes. No marcar HECHA antes de verificar todos los criterios.

## Pruebas requeridas

Ensayar paquete manipulado y clave revocada; reconstruir desde manifiesto y ejecutar instalación limpia.

Pruebas propuestas: todavía NO EJECUTADAS. Si una prueba depende de API pagada, evaluador externo, claves operativas o entorno no disponible, registrar el bloqueo específico. No cambiar el criterio para omitirla. Toda interacción externa debe limitarse al alcance autorizado; una ficha no autoriza contratar personas, enviar mensajes ni gastar dinero.

## Criterios de aceptación

- [ ] AC-1: Una release se vincula a fuente y semilla concretas.
- [ ] AC-2: Firma extranjera, checksum incorrecto y rollback no autorizado se detectan.
- [ ] AC-3: Auditoría incluye dependencias estáticas y procesos externos.
- [ ] AC-4: CI de release conserva la comprobación sin Rust.
- [ ] AC-COMÚN: no se degradó compatibilidad obligatoria, política de efectos ni independencia alcanzada.
- [ ] AC-EVIDENCIA: cada criterio tiene comando o procedimiento reproducible, resultado y referencia de artefacto.
