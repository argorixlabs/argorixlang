# MAT-002 — Fronteras de confianza de ArgorixLang

Estado: contrato de arquitectura, no certificación de la implementación. Base inspeccionada: `5d73d663bf5b85fd71bdd0cbc1ac1636959d7e64` (2026-09-18). Despliegue primario confirmado por el usuario: CLI y runtime local. El demo HTTP es una superficie secundaria y condicional. [Catálogo legible por máquina](claims.json); [modelo de amenazas](../ArgorixLang-threat-model.md); [producto objetivo](product-contract.md).

## Regla fundamental

El texto de un programa, una respuesta de modelo, un mensaje entre agentes, un campo DID/VC/jurisdicción, un manifest, una política declarada y una traza interna son **datos**, no autoridad. Una decisión de ejecución debe derivar de identidad autenticada, capacidad vigente, política en el punto de despacho, límites del host y registro de efecto observable. Un componente que falla, falta o no se puede verificar no debe convertir `DENY`, `REVIEW` o `UNKNOWN` en `ALLOW`.

La VM actual valida y planifica ciertas operaciones, pero `sandboxed_external` queda en `planned` con `external_execution_enabled: false` en `crates/argorix_vm/src/vm.rs`. El proveedor ejecutable permitido por `crates/argorix_provider/src/registry.rs` es el simulado (salvo el feature de investigación `eval-tripwire`). No atribuir a esta VM aislamiento de procesos/red/FS, ejecución real de herramientas, autenticación remota o contención de efectos. El demo `demo/argorix-chatbot-runtime` sí puede llamar a una API de modelo desde Node; ello no convierte esa llamada en efecto gobernado por el núcleo.

## Actores, activos y flujos

Actores: desarrollador, operador y propietario de política local; proveedor externo de modelo/herramienta; agente remoto futuro; verificador independiente; atacante que controla entradas o un paquete; atacante local con acceso a archivos; dependencia/build comprometido. No se supone que el atacante ya controle el kernel o la cuenta del operador: bajo tal compromiso las garantías del proceso local no son defendibles.

Activos: código fuente y módulos; bytecode; política y concesiones; secretos; estado y presupuesto; efectos externos; registros y bundles de evidencia; claves/anclas; binarios de release.

## Invariantes que deben implementar tareas posteriores

1. **Autoridad:** cada operación real tiene sujeto autenticado, recurso, acción, alcance, presupuesto y caducidad. La autorización se comprueba justo antes del efecto. Ausencia/expiración/revocación/incoherencia → denegación; `REVIEW` exige aprobación separada sin autoconversión a permiso (MAT-006/012/013).
2. **Identidad:** nombre, DID, VC, pasaporte, jurisdicción y etiqueta legal son metadatos hasta verificación contra ancla y política explícita. Fallo/timeout de identidad o ancla desconocida → no ejecutar acción que requiera identidad (MAT-007/012/015).
3. **Host:** el runtime debe recibir del OS límites efectivos de proceso, red, FS, memoria y tiempo; si el perfil no puede imponer un límite requerido, esa capacidad se deshabilita y el perfil queda fuera de soporte para la garantía, sin simular éxito (MAT-011/024).
4. **Almacenamiento:** validar versión, integridad y transacción antes de recuperar. Estado ilegible o incierto → detener/deshabilitar efectos y exigir reconciliación; no reintentar automáticamente una acción no idempotente (MAT-010/017).
5. **Evidencia:** verifier independiente rechaza rutas exteriores, hashes/firma/ancla incorrectos y fuentes no vinculadas. Sin ancla, sólo se puede afirmar consistencia interna. Ausencia de sensor externo impide afirmar ausencia de efecto (MAT-007/018/026).
6. **Secretos:** configuración del operador permanece fuera de fuente, bytecode, trazas y respuestas. Filtración o error de redacción → parar publicación/efecto y rotar; archivos de clave requieren permisos y ciclo definido (MAT-007/012/018).
7. **Plataformas:** las garantías se prueban por separado en Ubuntu 24.04 x86-64 y Windows 11 x86-64 sobre el artefacto de release; un pase en una no se extrapola a otra (MAT-011/023/026).
